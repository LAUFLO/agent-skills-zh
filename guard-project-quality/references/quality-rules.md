# 通用项目质量规则

## 1. 约束层级

按以下优先级执行：

1. 仓库现有 `AGENTS.md`、贡献指南和框架约定；
2. 格式化、分析器、测试与 CI 等可执行规则；
3. 本 Skill 的通用建议。

优先把重要规则转成工具配置或 CI 检查，不只写在文档中。

## 2. 编码与仓库卫生

- 文本默认使用 UTF-8；发现乱码时先按 UTF-8 重读，再根据 BOM 或项目元数据判断。
- 统一换行、缩进、文件末尾换行和尾随空格。
- 不提交密钥、个人配置、缓存、依赖、构建产物或临时文件。
- 将生成文件明确放入生成目录，并在审计、格式化和分析器中精确排除。
- 根目录只保留入口、配置、许可证和项目说明；业务源码进入技术栈惯用目录。

## 3. 结构与依赖

- 一个模块只承担一个主要职责。
- 推荐依赖方向：UI/API → Application → Domain；Infrastructure 实现边界接口。
- Domain 不依赖 UI、数据库驱动、网络客户端或具体框架。
- 跨模块共享代码应有清晰所有者，不建立无边界的 `common` 或 `utils` 大杂烩。
- 避免循环依赖、隐藏全局状态和跨层直接访问。
- 保留框架惯例：例如 Go 的单包根目录、Next.js 路由目录或 Django 应用目录可以作为明确例外。

## 4. 文件规模

- 500 行以上：警告并检查是否混合职责。
- 800 行以上：默认阻断，要求拆分或记录例外理由。
- 不计算第三方、生成文件、迁移、锁文件、快照和纯声明式数据。
- 按领域职责、组件、协议适配器或生命周期拆分；不要机械按行数切割。
- 拆分时同步更新构建清单、命名空间、导入、资源嵌入和测试入口。

## 5. 命名与注释

- 名称表达业务含义，避免 `Manager2`、`HelperNew`、`CommonUtil` 等弱名称。
- 公共接口保持稳定；不兼容变化必须显式说明。
- 注释解释原因、限制和不变量，不重复代码表面行为。
- TODO 必须包含可执行说明；项目要求时附问题编号。

## 6. 错误、日志与安全

- 不吞掉关键异常；将用户可理解的信息与诊断详情分开。
- 不在日志中记录密钥、令牌、聊天正文或不必要的个人路径。
- 外部输入在边界处验证；文件、网络和进程操作设置合理限制。
- 依赖升级通过锁文件、测试和安全扫描验证。

## 7. 测试策略

- 业务规则使用快速、确定性的单元测试。
- 文件、数据库、进程、网络或 UI 边界使用集成测试。
- 修复缺陷时补充修复前失败、修复后通过的回归测试。
- 测试覆盖空值、边界、失败路径、并发或重入风险。
- 不通过降低断言、删除测试或无边界重试来消除失败。

## 8. CI 质量门禁

至少包括：

- 格式或 lint；
- 静态分析或编译器警告；
- 测试；
- 构建；
- 适用时的依赖与安全检查。

新项目应让警告策略明确且可逐步收紧。现有项目先记录基线，再避免新增告警，不一次性掩盖历史问题。

## 9. 新项目与现有项目

- 新项目：从第一天建立目录、测试、格式化、分析器和 CI。
- 现有项目：先测量，再小步整理；保持行为、打包、部署与公开 API。
- 大规模重组必须有路径映射、构建入口更新和回归验证。
