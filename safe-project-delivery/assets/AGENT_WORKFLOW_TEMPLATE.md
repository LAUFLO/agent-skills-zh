# 项目交付规则

将本模板放入当前 Agent 支持的项目指令文件后，按项目实际命令补充测试和发布入口。

## 授权边界

- “检查/诊断”：只读，不修改。
- “修改/修复”：修改并测试，不提交、不推送。
- “提交”：只提交到工作分支。
- “创建 PR”：推送并创建 PR，不合并。
- “合并”：检查 CI 后合并，不发布。
- “发布”：合并后才创建标签、Release 和上传产物。

不要因为用户说“完成”“继续”或“处理好”而自动扩大授权。

## Git

- 修改前读取项目指令并检查分支、远程和工作区状态。
- 不直接在默认分支实现修改；从最新默认分支创建工作分支。
- 保留已有修改，不使用 `git reset --hard` 或强制覆盖。
- 不使用 `git add -A`；只暂存本次明确修改的文件。
- 提交前检查暂存文件、暂存 diff 和空白错误。
- 未经明确授权，不推送、不创建 PR、不合并、不发布。

## 修改与测试

- 实施满足需求的最小完整改动。
- 修复问题时补充回归测试。
- 使用项目已有测试和构建命令。
- 先运行受影响测试，再运行项目要求的完整检查。
- 如有测试无法执行，说明具体原因，不声称全部通过。

## PR 与合并

- PR 只包含当前任务文件。
- PR 正文简述变更、原因和验证结果。
- 创建 PR 后默认停止。
- 合并前检查目标分支、head SHA、CI、评审和冲突。
- 合并后确认远程默认分支最终 SHA。

## 发布

- 优先使用项目已有发布工作流或脚本。
- 版本改动通过 PR 合并后再发布。
- 不从功能分支、旧提交或脏工作区打标签。
- 创建标签前检查同名标签和 Release 不存在。
- 发布后核对默认分支、标签、Release、产物版本和校验值。

发布说明仅保留实际存在的项目：

```markdown
- 新增：……
- 修复：……
- 优化：……
```

每项一句话，不写实现细节、测试过程或文件清单。
