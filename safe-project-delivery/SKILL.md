# 安全项目交付

## 核心原则

- 先确认用户授权到哪一层，再执行该层及以下操作。
- 把“修改代码”“提交”“创建 PR”“合并”“发布”视为五个独立阶段。
- 不因为用户说“完成”“处理好”或“继续”而自动扩大到推送、合并或发布。
- 优先遵循项目自己的 `AGENTS.md`、贡献指南、分支保护、CI 和发布脚本。
- 保留用户已有改动；不要清理、覆盖或顺手提交不属于当前任务的文件。

## 1. 确定授权层级

按用户的明确请求选择最高授权层级，完成后停止：

| 层级 | 允许的操作 |
|---|---|
| 检查 | 读取仓库、诊断、报告，不修改 |
| 修改 | 编辑文件并验证，不提交、不推送 |
| 提交 | 在工作分支提交，不推送 |
| PR | 推送工作分支并创建 PR，不合并 |
| 合并 | 检查 PR 与 CI 后合并，不发布 |
| 发布 | 合并后升级版本、创建标签或 Release、上传产物并验证 |

若用户同时明确要求多个阶段，可连续完成到最高授权层级。遇到必须新增外部权限、选择发布策略或执行范围显著扩大的情况，停止并请求确认。

## 2. 盘点仓库

在修改前：

1. 找到仓库根目录、当前分支、默认分支和远程仓库。
2. 读取适用的 Agent 指令、贡献指南和构建文档。
3. 检查工作区、暂存区和未跟踪文件。
4. 识别测试、构建、版本和发布入口。
5. 判断用户已有改动是否与本任务重叠。

工作区不干净时，不假设所有改动都属于当前任务。能隔离则继续；存在覆盖风险时先说明具体冲突。

## 3. 隔离修改

- 不直接在 `main`、`master` 或检测到的默认分支上实现代码修改。
- 若即将修改且当前位于默认分支，先从最新默认分支创建工作分支。
- 遵循项目分支命名约定；没有约定时，Codex 使用 `codex/<slug>`，其他 Agent 使用自身名称或 `agent/<slug>`。
- 不使用 `git reset --hard`、强制检出或其他会丢失用户改动的命令。
- 只修改任务所需文件；不要顺手格式化整个仓库。

如果修改已在默认分支工作区中开始，先确认切换分支不会覆盖文件，再带着当前工作区创建分支，不要先丢弃改动。

## 4. 修改与验证

1. 先复现或明确需求，再实施最小完整改动。
2. 为修复补充能在修复前失败、修复后通过的回归测试。
3. 优先运行受影响范围的测试，再运行项目要求的完整检查。
4. 使用仓库已有命令；不要仅凭生态习惯发明发布命令。
5. 记录实际执行的命令、通过结果和未执行原因。

当项目类型或发布入口不明确时，读取 [references/release-strategies.md](references/release-strategies.md)。

## 5. 提交与 PR

只有授权到相应层级时才执行：

- 使用显式文件列表暂存，例如 `git add -- <files>`；不要使用 `git add -A`。
- 检查 `git diff --cached --name-status`、`git diff --cached --check` 和暂存 diff。
- 提交信息简短描述意图，不伪造测试结果。
- 推送前确认分支和远程目标。
- PR 正文只写变更、原因和验证结果；不要把无关工作区内容写入 PR。
- 创建 PR 后默认停止，不自动合并。

## 6. 合并

只有用户明确要求合并时：

1. 确认 PR 指向正确默认分支且 head SHA 未变化。
2. 检查必需 CI、评审和冲突状态。
3. 使用仓库允许的合并方式。
4. 合并后读取远程默认分支最终 SHA。
5. 不把“PR 已创建”当作“已合并”。

如果必需检查仍在运行，等待或启用项目允许的自动合并；不要绕过保护规则。

## 7. 发布

只有用户明确要求发布时：

1. 检查版本规则、已有标签、发布说明和项目发布入口。
2. 优先复用现有 CI、脚本和托管平台 Release；不要并行维护第二套发布方式。
3. 按项目规则升级版本；未定义时才使用语义化版本：
   - 修复或兼容优化：补丁版本。
   - 向后兼容的新功能：次版本。
   - 不兼容变更：主版本。
4. 将版本、测试断言、清单和发布说明保持一致。
5. 先通过 PR 合并发布改动，再从远程默认分支最终 SHA 创建标签或触发发布工作流。
6. 创建标签前确认标签不存在；不要从功能分支、旧 SHA 或脏工作区发布。
7. 发布后核对默认分支 SHA、标签目标、Release 状态、产物名称、版本和校验值。

发布说明保持简短，只保留实际存在的分类，每项一句话：

```markdown
- 新增：……
- 修复：……
- 优化：……
```

不要在用户发布说明中罗列实现细节、测试过程或文件清单，除非用户明确要求。

## 8. 跨 Agent 使用

本 Skill 会被 Codex 自动加载，其他 Agent 不一定识别 Codex Skill。需要统一多个 Agent 时，将 [assets/AGENT_WORKFLOW_TEMPLATE.md](assets/AGENT_WORKFLOW_TEMPLATE.md) 的规则复制到目标项目所支持的 Agent 指令文件中。复制或修改项目规则属于项目变更，必须先获得用户授权。

## 交付格式

结果中明确区分：

- 已修改但未提交。
- 已提交但未推送。
- 已创建 PR 但未合并。
- 已合并但未发布。
- 已发布并完成远程验证。

只报告实际确认成功的操作，并附上相关分支、提交、PR、标签或 Release。
