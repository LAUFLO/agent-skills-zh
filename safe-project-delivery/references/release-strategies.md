# 跨项目发布策略

仅在项目类型、版本来源或发布入口不明确时读取本文件。

## 发现顺序

1. 读取项目 Agent 指令、贡献指南和发布文档。
2. 检查默认分支、远程仓库、分支保护和近期标签。
3. 检查 CI/CD 配置和项目脚本。
4. 检查版本来源、锁文件和制品配置。
5. 从最近一次成功发布还原项目真实流程。

不要因发现某个生态文件就跳过项目自己的说明。

## 常见入口

| 线索 | 可能的测试、构建或版本来源 |
|---|---|
| `package.json` | `scripts`、包版本、Node 构建 |
| `pyproject.toml` | Python 包版本、测试和构建配置 |
| `.csproj`、`Directory.Build.props` | .NET 版本、编译和打包 |
| `Cargo.toml` | Rust crate 版本、测试和构建 |
| `go.mod`、`Makefile` | Go 测试、编译和项目封装命令 |
| `pom.xml`、`build.gradle*` | Java/Kotlin 版本、测试和打包 |
| `.github/workflows/` | GitHub CI、标签和 Release 自动化 |
| `.gitlab-ci.yml` | GitLab CI 与发布任务 |
| `scripts/`、`tools/`、`build.*`、`release.*` | 项目自定义入口 |

同一项目可能存在多个版本来源。搜索现有版本字符串和发布校验，确认需要同步的文件，不要盲目替换所有数字。

## 选择发布方式

按以下优先级：

1. 已验证的托管平台发布工作流。
2. 项目已有发布脚本。
3. 项目文档规定的手动步骤。
4. 用户确认后才建立新流程。

若工作流接收提交 SHA，使用远程默认分支合并后的最终 SHA。若工作流会自行创建标签，不要提前手动创建同名标签。

## 发布前检查

- 默认分支包含目标改动。
- 工作区中的无关改动未进入提交。
- 所需测试和构建已通过。
- 版本号与发布说明一致。
- 目标标签和 Release 不存在。
- 产物名称包含正确版本。
- 凭据和权限足以完成发布。

## 发布后检查

- 远程默认分支 SHA 与预期一致。
- 标签准确指向该 SHA 或项目规定的发布提交。
- Release 不是草稿或预发布，除非用户要求。
- 必需产物均已上传且状态正常。
- 可执行文件或包的内部版本正确。
- 校验文件与远程产物匹配。

只把远程可观察结果作为发布成功依据。本地构建成功不等于已经发布。
